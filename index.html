01 AWS · self-directed · view repo →

A web tier that heals itself

Two Availability Zones behind a load balancer, an Auto Scaling Group that replaces failed instances, and content pulled from a private S3 bucket with no credentials on disk. Then I terminated instances to see what held.

High availability

An internet-facing Application Load Balancer spreads traffic across an Auto Scaling Group in two Availability Zones. Losing a zone doesn't lose the site.

No static credentials

Instances read from a private S3 bucket through an IAM role scoped to one bucket ARN. No access keys anywhere on the host.

Boot-time provisioning

A launch template and user data script install Apache and pull content from S3 on first boot, so every replacement is identical to what it replaced.

Health checks that mean something

ELB health checks on the Auto Scaling Group, so an application serving errors gets replaced — not just a host that stopped responding.

The three bugs — all silent, none where I was looking

a missing shebang threw the whole script away

Instances passed 2/2 EC2 status checks while the load balancer marked them unhealthy, and the ASG looped replacing them. The system log had it: without #!/bin/bash, cloud-init discarded the user data. Apache was never installed.

a health check passed on the wrong page

The S3 copy failed, the script aborted — but Apache was already running, and its default "It works!" page returns 200. A health check on / proves something answered, not that the deploy worked. Real checks hit a path the deploy creates.

a filename mismatch, and a filter hiding the fix

Windows had renamed the upload index (2).html, so the script's fetch 404'd. Separately, a leftover "unhealthy" filter in the console hid two healthy targets — I spent minutes debugging a system that had already recovered.

02 AWS · self-directed · running nightly · view repo →

Backups that can only delete their own

A Lambda on a 3 AM schedule snapshots every EBS volume tagged Backup=true and deletes its own snapshots after 7 days. The rule that matters — never delete what you didn't create — is enforced twice: once in the code, once in IAM.

Enforced twice

The code only lists snapshots tagged ManagedBy. The IAM role can only call DeleteSnapshot on that tag — so a bug in the code still can't touch a manual backup.

Can't fake the tag

The role may only add tags while creating a snapshot. Without that, "delete only tagged" means nothing — a role that can tag anything can tag anything as deletable.

Dry run first

A DRY_RUN switch reports what would be created and deleted without doing it. Every destructive step was run dry before it ran for real.

Delete before create

Cleanup runs first, so a snapshot made in a run can never be caught by that same run's retention check.

What almost went quietly wrong

a lowercase tag key

The volume was tagged backup, not Backup. Tag keys are case-sensitive — it would have run every night, found nothing, reported success, and backed up nothing. Caught before the first run.

a 100 GiB default, twice

The volume form defaults to 100 GiB, and EBS volumes can't shrink. Swapped for a 1 GiB volume that fits the free tier.

a log that looked wrong and wasn't

An 08:33 snapshot logged as 13:33. AWS logs in UTC — the difference between "the job ran at the wrong time" and reading the log wrong.
