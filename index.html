A web tier that heals itself

Two Availability Zones behind a load balancer, an Auto Scaling Group that replaces failed instances, and content pulled from a private S3 bucket with no credentials on disk. Then I terminated instances to see what held.

High availability

An internet-facing Application Load Balancer spreads traffic across an Auto Scaling Group in two Availability Zones. Losing a zone doesn't lose the site.

No static credentials

Instances read from a private S3 bucket through an IAM role scoped to one bucket ARN. No access keys anywhere on the host.

Boot-time provisioning

A launch template and user data script install Apache and pull content from S3 on first boot, so every replacement is identical to what it replaced.

Health checks that mean something

ELB health checks on the Auto Scaling Group, so an application serving errors gets replaced — not just a host that stopped responding.

The three bugs — all silent, none where I was looking

a missing shebang threw the whole script away

Instances passed 2/2 EC2 status checks while the load balancer marked them unhealthy, and the ASG looped replacing them. The system log had it: without #!/bin/bash, cloud-init discarded the user data. Apache was never installed.

a health check passed on the wrong page

The S3 copy failed, the script aborted — but Apache was already running, and its default "It works!" page returns 200. A health check on / proves something answered, not that the deploy worked. Real checks hit a path the deploy creates.

a filename mismatch, and a filter hiding the fix

Windows had renamed the upload index (2).html, so the script's fetch 404'd. Separately, a leftover "unhealthy" filter in the console hid two healthy targets — I spent minutes debugging a system that had already recovered.

Backups that can only delete their own

A Lambda on a 3 AM schedule snapshots every EBS volume tagged Backup=true and deletes its own snapshots after 7 days. The rule that matters — never delete what you didn't create — is enforced twice: once in the code, once in IAM.

Enforced twice

The code only lists snapshots tagged ManagedBy. The IAM role can only call DeleteSnapshot on that tag — so a bug in the code still can't touch a manual backup.

Can't fake the tag

The role may only add tags while creating a snapshot. Without that, "delete only tagged" means nothing — a role that can tag anything can tag anything as deletable.

Dry run first

A DRY_RUN switch reports what would be created and deleted without doing it. Every destructive step was run dry before it ran for real.

Delete before create

Cleanup runs first, so a snapshot made in a run can never be caught by that same run's retention check.

What almost went quietly wrong

a lowercase tag key

The volume was tagged backup, not Backup. Tag keys are case-sensitive — it would have run every night, found nothing, reported success, and backed up nothing. Caught before the first run.

a 100 GiB default, twice

The volume form defaults to 100 GiB, and EBS volumes can't shrink. Swapped for a 1 GiB volume that fits the free tier.

a log that looked wrong and wasn't

An 08:33 snapshot logged as 13:33. AWS logs in UTC — the difference between "the job ran at the wrong time" and reading the log wrong.

The "Was this you?" fraud alert

The text your bank sends when something strange hits your card — built end to end. A swipe is approved, scored against the cardholder's history off a DynamoDB stream, and if it looks wrong, an email goes out with one link. Tap lock and the very next swipe is declined.

Approve fast, score right after

The card reader never waits on fraud scoring. It approves and records; the detector scores a moment later off the stream — the way card networks keep checkout fast.

Scanner-proof links

Email security scanners open links on their own. So opening the link only shows the buttons — the lock happens on an explicit button press (POST), never on a visit.

No double anything

Swipes are idempotent on their transaction ID, alerts resolve with a conditional update — click twice and the second click gets "Already handled."

Fraud never becomes normal

Flagged charges aren't folded into the card's average, so one big fraud can't raise the baseline and hide the next. One open alert per card — six charges, one email.

What broke

a stream that wouldn't move on

The detector's code was wrong in the console, and a stream-triggered Lambda retries the same batch until it succeeds. Nothing was lost — 60 swipes queued — and caught up unevenly once fixed, because each stream shard backs off separately.

fraud detected, nobody told

A missing setting made my code skip the email silently: fraud caught, alert written, no one notified. Fixed in the code — missing config now logs CONFIG ERROR, and every alert says whether its email was sent.

no terminal, so the simulator became a Lambda

CloudShell is locked on new accounts. The traffic generator moved into a fourth Lambda, driven from the console — the whole system runs inside AWS.

04 Terraform · serverless · in daily use · view repo →

A job tracker that logs itself

I built this to run my own job search. When an application confirmation lands in Gmail, it's logged within the hour; a rejection or a "let's schedule a call" moves the status on its own. Every morning it nudges me about anything gone quiet, and every Sunday it emails the week's numbers. The first of my projects built entirely as code — 32 resources, one terraform apply.

One command, 32 resources

Three Lambdas with their own roles, a table, an API with six routes, two schedules, a topic, and the key that protects it — built by terraform apply and removed by terraform destroy.

Changes touch only what changed

Fixing a bug in the web page produced a one-line plan: 0 to add, 1 to change. Terraform hashed the code, updated one function, and left the other 31 alone. Six seconds to ship.

AI with a backup

Amazon Nova reads each email. If the model fails for any reason, pattern-matching takes over — so an email is never dropped because a model call did.

No duplicates, no nagging

Each email maps to one ID, so it can't be logged twice; a confirmation for a job already tracked links to it instead. Each follow-up reminder fires at most once a week.

What broke

the AI had no allowance on a new account

ThrottlingException: Too many tokens per day — after four short emails. New AWS accounts start with almost no Bedrock quota. The fallback carried every email correctly, and the fix made it fail fast (~2 s per email instead of ~10).

an empty key from the wrong folder

Every sync got 401. The key had been read with terraform output from system32, where there's no state, so it was blank. Terraform state is per-directory.

"updated −1 days ago"

The laptop clock was a few seconds behind AWS, so a brand-new entry looked like it came from the future. Clamped at zero — and the fix became the proof that the update path works.

05 Fintech · Terraform · 45 tests · view repo →

KeitaBank: a bank that balances to the cent

A to-do list that saves twice shows a duplicate. A bank that saves twice takes someone's rent. KeitaBank is a small working bank — real sign-in, accounts with account numbers, transfers between people, card-style payments, and a live money tracker — built to get that part right. The money is fake. The guarantees are the ones a real bank needs.

A payment happens once

Every payment carries a key the browser makes once per submit, stored in the same transaction as the money. A double-tap or a network retry returns the first result and moves nothing.

All of it, or none of it

A transfer is four writes — two balances, two ledger lines — sent to DynamoDB as one transaction. There is no moment where money has left one account and not reached the other.

Never below zero, even in a race

Each balance update only applies if the balance is still what was read. Five $200 transfers fired at once from a $597.40 account: two succeed, three are refused, balance ends at $197.40.

The gateway checks the token

Cognito signs customers in; API Gateway verifies every token before the function runs. A customer's ID comes from that token and never from the request, so nobody can name someone else's account as the source.

What the tests caught

a wrong-shaped request crashed the function

A JSON list where an object was expected raised an exception instead of returning 400. Every request body is now checked first.

the balance chart began with a cliff

The chart is drawn by walking backwards from today's total, which put a vertical line from $0 to $1,000 at the left edge. It now starts at the first deposit.

the books have to balance

The last tests add up every ledger line and compare it to every balance. They agree to the cent — and the first real deploy, 22 resources in one terraform apply, worked on the first try.
